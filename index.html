01 / Systems

ClimbStream

C++20 · CMake · GoogleTest · 2026

Source & setup ↗

I used climbing events to make stream recovery easier to understand.

A session starts, an attempt begins, and the climber either sends the route or fails the attempt. Those events need to stay in order. I built ClimbStream so I could inspect how they are stored, what a consumer has processed, and what happens when it restarts or replays old events.

Starting with one node

I kept the first milestone in one process on one node. That lets me check the basics before adding concurrency and networking: events from the same session stay in order, offsets survive reopening the log, and each consumer tracks its own progress.

Producer→Session partition→JSONL log→Consumer + offset

Deciding when to save progress

The broker uses the session ID to choose a stable partition, then assigns that partition's next offset. It appends each event as a JSON line. When the log reopens, it checks that the stored offsets have no gaps. I store consumer offsets separately so consumers can move independently.

The consumer processes an event before saving its offset. If processing fails, it can retry. If it crashes after processing but before saving, it will process that event again on restart. That is the tradeoff behind at-least-once processing. Replay reads the history without changing the live consumer's position.

Run the C++ demo

With C++20 and CMake 3.24+, clone the repository and build it. CMake downloads the pinned dependencies.

cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure

For a single-configuration build, publish two events and run a consumer with a persistent ID. On Windows, use the executable location produced by your CMake generator, which may include a configuration folder such as Debug.

./build/climbstream-producer data/logs session-demo SESSION_STARTED event-1
./build/climbstream-producer data/logs session-demo ATTEMPT_STARTED event-2
./build/climbstream-consumer data/logs data/offsets demo-consumer

Publish a third event, then run the same consumer again. It should emit only the new event. For replay, pass --replay <partition> 0, using the session's actual partition. The committed offset should stay unchanged. Both CLIs use four partitions; keep that count consistent when reopening data.

Current scope: persistent logs, independent consumer positions, restart recovery, and explicit replay. Concurrent ingestion, replication, networking, and the climbing UI are planned. The engine does not yet guarantee crash-consistent storage for production use.

TC Token Optimizer

JavaScript · OpenCC · Claude Code hooks and CLI · 2026

Source & setup ↗

I wanted to reduce token use without losing the task's instructions.

TC Token Optimizer looks at the token overhead of Traditional Chinese in coding-agent workflows. Shortening the text only helps if the agent still has the references and instructions it needs to do the work.

Rewriting the prompt before it reaches the agent

Claude Code's tool hooks can change tool inputs, but its prompt-submit hook cannot replace a user prompt before it enters context. So I use a CLI wrapper to rewrite prompts before Claude Code receives them. Hooks handle source reads and traces, and a skill keeps responses concise.

Checking what the compression preserves

The experiment compares original and compressed fixtures using js-tiktoken with cl100k_base. A fixture audit checks that the prompt pairs keep their constraints. It also compares a proxy estimate with the tokenizer count and allows a difference of up to eight percentage points.

The six recorded fixtures use approximately 61 to 85% fewer tokens after compression. But the wrapper fits prompts into a template based on a hint table. It can silently drop instructions that the table does not cover. The fixture audit checks those examples; it cannot promise that every new prompt keeps its meaning.

Run the token comparison

Clone the source, install its Node.js dependencies, and run the checks from the repository root.

npm install
npm test
npm run audit:fixtures
npm run measure:tokens

Open test/results/token-savings.md beside the original and compressed fixtures. Check the instructions that remain as well as the token counts. To take the experiment further, try a prompt with an unusual preservation rule and check whether the rule survives before letting an agent act on it.

Measurement limits: these results cover the recorded fixtures and the stated tokenizer. They do not measure billing savings. Converting Traditional Chinese to Simplified Chinese alone does not account for the reduction. If a prompt must stay word for word, bypass the lossy wrapper.

03 / Desktop applications

Go Desktop

C# · .NET 9 · Avalonia · KataGo · 2026

Source & setup ↗

The app needs to handle a legal game before the AI opponent matters.

For Go Desktop, that means keeping the board correct through captures, illegal moves, passes, and scoring. I also wanted it to be playable before the user sets up an external AI engine.

Keeping the rules local

I built a local rules engine for captures, suicide prevention, ko, resignation, and Chinese area scoring. The Avalonia app has 9×9, 13×13, and 19×19 boards, color selection, and setup stones. KataGo is optional; its difficulty settings change the visit and time budgets.

Without KataGo, the app uses a weak local opponent. That lets someone try the game before configuring the stronger engine. The demo follows the same order: check that the moves are legal, then add KataGo. You can export a game as SGF to review it outside the app.

Try the desktop app

Follow the repository's Windows setup instructions for the .NET/NuGet paths, then launch the app:

dotnet run --project src\GoDesktop.App\GoDesktop.App.csproj

Start with a 9×9 board and the local opponent. Use setup stones to arrange a capture, start the game, and play the capturing move. Then explore suicide prevention and ko with prepared positions. Pass to reach scoring and export the game as SGF.

Then open the KataGo tab, set the executable and model paths, save the settings, and compare difficulty levels. You can check how the rules work before installing the stronger engine.

Check in the demo: legal board changes, scoring at the end of a game, and SGF export. The fallback lets you play immediately; KataGo is the stronger opponent once its executable and model are configured.

PyTorch · ResNet-18 · Jan–May 2025

Using a pretrained model to classify recycling images.

I fine-tuned a frozen-backbone ResNet-18 with augmentation, learning-rate scheduling, and early stopping. The reported results were 84.7% accuracy and 94% F1. Both scores help describe performance, but interpreting their difference requires the class distribution and the F1 averaging method.

Police Stop Bias Analysis

scikit-learn · neural networks · Aug–Dec 2024

Testing how well models predict without demographic features.

I evaluated nine models on 3.8M+ Virginia police-stop records. Part of the work was reducing a roughly one-million-column one-hot feature space to about one thousand columns. Test accuracy improved from 71.85% to 74.50% without demographic features. Choosing how to represent the data mattered alongside choosing the model.

The accuracy result does not prove fairness. Other inputs may still act as proxies for demographics.

Demo idea: compare errors across groups

A next demo could compare feature-space size and test performance, then examine subgroup error rates before making a fairness claim. This page does not include that subgroup evaluation or an interactive dashboard.

Cross-Lingual Tokenization

Hugging Face Tokenizers · SentencePiece · Aug–Dec 2024

Comparing how tokenizers split different writing systems.

I compared tokenization across 30,000+ English, Japanese, and Chinese samples. For logographic languages, I proposed radical-based decomposition as another way to represent the text. The design question was what units the model should receive when the writing system changes.

Demo idea: show the token boundaries

A next demo could show multilingual examples with their token boundaries and counts, then compare the proposed radical decomposition with the existing representations. The proposal still needs validation before I can claim an improvement.

Congressional Apportionment ↗

Java · algorithms · 2024

The same population data can produce different seat allocations.

I built a command-line tool with Adams, Jefferson, and Huntington–Hill methods, configurable seat counts, and CSV/XLS/XLSX input. Run each method with the same dataset and seat count to see how the algorithm changes the allocation.

Compare the allocation methods

Build with the repository's Gradle wrapper and use Java 17 or later. From the directory containing the generated JAR and your input file:

java -jar Apportionment.jar example.csv 435 --adams
java -jar Apportionment.jar example.csv 435 --jefferson
java -jar Apportionment.jar example.csv 435 --huntington

Compare state-by-state allocations and verify that the allocated seats total the requested count.
